The Map Above the Waterline

One win, this lesson: hold the whole system in your head as seven modules, seven one-sentence contracts, and arrows that only point down. Everything else in this course zooms into a region of this map.

Seven contracts, one sentence each

ModuleContract
ModelsThe shared vocabulary — the domain types every other interface speaks; depends on nothing.
ParsingRaw sheet snapshot in, interpreted Block (plus warnings) out — pure, never touches the network.
SheetsFive async methods that are the only way bytes move between the app and Google.
StoresThe app's memory — observable state plus commands that mutate the cache and queue Sheet writes.
ProgressThe rules of "what's next" — pure progression math plus the active-session state machine.
LoadSuggestionEngineOne pure function: prescription in, suggested weight out (or nil).
ThemeNamed design tokens, reached through one environment key.

Three rules the arrows enforce

  1. Everything bottoms out in Models. Every solid arrow points downward, and the bottom of every chain is Models. That's why the domain glossary in CONTEXT.md is part of every interface's contract — parameters and return types are named in its terms.
  2. Views only see Stores, Progress, and Theme. No View imports SheetsClient or SheetParser. If a feature needs sheet data on screen, it arrives through a store's observable state, never by fetching.
  3. The outside world enters through one seam. The dashed green edge — protocol SheetsClient — is the only path to the network. Three adapters sit at that seam (live Google, local workbook for tests, UI-test fixtures), which is what makes the whole app testable offline.

One iceberg, up close: Sheets

The interface is more than the signatures. A caller of SyncCoordinator.sync must also know an invariant no type shows: pending writes are flushed before the pull, so local logs are never clobbered. Contracts like this are exactly what the reference records.

Check yourself — where does it go?

1. A View needs to display today's exercises. Which front door does it read?

Rule 2: Views only see Stores, Progress, and Theme. Sheet data reaches the screen as WorkoutStore.displayedSession — a View never fetches or parses.

2. You want a unit test to exercise a full sync without the network. Where do you swap in a fake adapter?

Rule 3: SheetsClient is the app's real seam — it already has three adapters (live, local workbook, UI-test fixtures). Everything above it runs unmodified.

3. New feature: warm-up weights calculated from the Training Max — pure math, no state. Its natural home?

Its contract is already "prescription in, weight out" — a pure function with no state. Extending that interface keeps the calculation testable in isolation and reusable from any presentation code.

Primary source

Watch John Ousterhout — "A Philosophy of Software Design" (Google talk, 2018), the origin of deep modules. Read it with the house correction in mind: this repo measures depth as leverage at the interface, not Ousterhout's line-count ratio (see the glossary).
