# Rest Timer alerts in the foreground and falls back to a local notification

The Rest Timer auto-starts a countdown after an intentional Set Log and must alert the athlete when it ends, including when the phone is set down, locked, in another app, or the app has been killed. It is purely local and never touches the Sheet or the network. The athlete's stated alert is a haptic ramp — a short tap on each of the final five seconds, then an extended buzz at zero.

iOS only lets an app emit Core Haptics (or any feedback generator) while it is foreground and active. The instant the app is backgrounded or the screen locks, that haptic ramp is impossible. The only mechanism that can reach the athlete when the app is not foreground is a local notification, which delivers a single sound plus the system vibration at its fire time — not a custom five-second ramp. Because the common gym case is a phone face-down on the floor with the screen off, the notification is in practice the primary alert and the haptic ramp is a bonus for when the athlete happens to be looking at the app.

A Rest is timed by an absolute deadline `Date`, not a decrementing counter. The live countdown is always `deadline − now`, so backgrounding and lock are handled for free by wall-clock math when the process is merely suspended. When the app is foreground and active, the app drives the live pill and plays the Core Haptics ramp (a light tap on each of the last five seconds, then an extended continuous buzz at zero — the extended buzz requires Core Haptics rather than a one-shot feedback generator). At Rest start the app also schedules a local notification for the deadline, with the default sound and system vibration. If the app is foreground when the deadline arrives, the in-app haptics play and the notification is suppressed; otherwise the notification is the alert. The app reschedules the notification when a new log restarts the Rest, and cancels it when the Rest is dismissed, when the origin Set Log is deleted, or on Move On out of the Session — all while the app is alive. Notification authorization is requested once at startup, after onboarding; a denial degrades the feature to foreground-only haptics with no loss of in-session behavior.

The app keeps the active Rest in memory only; it is not persisted to disk. A suspended process retains the deadline, so the pill resumes correctly on return to foreground. A full app kill drops the in-memory pill, but the OS still holds the scheduled notification, so the end-of-Rest alert survives the kill even though the pill does not. This accepts a minor incoherence — after a kill the alert can fire with no corresponding pill, and a notification can occasionally fire for a Rest the athlete would have cancelled had the app stayed alive — in exchange for no persistence machinery.

AlarmKit (iOS 26) was considered and rejected for the core feature. It would cover background alerting and Lock Screen / Dynamic Island presence in one system-managed component and survive app kills natively, but it presents a loud, interruptive system-alarm experience that is itself a destination — the opposite of the ambient, non-blocking pill the athlete asked for. ActivityKit Live Activities and the Dynamic Island are deferred to a second phase; they add visual continuation on the Lock Screen and Dynamic Island but cannot author custom background haptics, so they complement rather than replace the notification fallback. A pure foreground-only design with no notifications was rejected because it fails the resilience requirement: a Rest that ends while the phone is locked or away would never alert the athlete.
