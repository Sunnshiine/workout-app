The mental model

Think of Ralph as a parent process with one hard boundary. The parent decides what should happen and what may be published. The engine only performs a scoped agent turn and returns a normalized result.

  • Python is the source of workflow truth. Selection, issue contract capture, PR target resolution, gates, repair, labels, and publishing live in deterministic code.
  • Engines are replaceable turn runners. Codex SDK, Claude SDK, CLI fallback, and fake dry-run engines all return the same PhaseResult.
  • GitHub is changed only after gates and policy pass. Ralph uses draft or ready PRs, keeps successful issues open until merge, and preserves blocked code in rescue PRs.

What changed from shell Ralph

The old shape mixed orchestration and execution in one long shell path. The new shape splits parent decisions from agent turns, which makes failure handling and PR lifecycle rules testable.

Previous shell-owned shape

1
Shell selects and runs agents One script owns issue choice, worktree setup, prompts, gate commands, and publishing.
2
Promise lines signal phase status CLI output is parsed for completion or blocked lines.
3
Failures are harder to preserve Code can be stranded in a local worktree after a later gate fails.
4
Publishing can target main or a branch Routing behavior depends on legacy options and issue directives.

Current Python target shape

1
Python selects and freezes the contract Later permissions come from the pre-agent snapshot, not prompt compliance.
2
Engine runs one scoped phase SDK, CLI, and fake engines normalize to one PhaseResult shape.
3
Python gates and applies authority policy UI-test edits, visual baselines, repair attempts, and redaction are mechanical.
4
Publishing is PR-only Successful branches use closing commits. Blocked code becomes a draft rescue PR.

Engine strategy

The engine layer is intentionally narrow. It should not know which issue is eligible, whether UI tests may be edited, or whether a PR can be marked ready.

Issue and PR lifecycle

The most important product behavior is not the engine choice. It is what Ralph does with code after a phase finishes.

1
Capture the issue contract PRD membership comes from PRD: #N. UI-test edit authority comes from the exact issue body line.
2
Choose a deterministic branch One-off issues use ralph/issue-N. PRD-scoped issues stack on ralph/prd-N.
3
Gate before publishing Swift, Xcode, UI, visual, lint, and authority gates report structured pass or fail states.
4
Publish success to a PR branch Ralph adds agent-implemented, removes ready-for-agent, and leaves the issue open until PR merge.
5
Preserve blocked code Blocked work becomes a draft rescue PR with Refs #N, sanitized context, and no closing keyword.
6
Attempt one UI repair when allowed A first UI-owned gate failure gets one repair pass. A second failure escalates to human review.
agent-implemented ready-for-agent removed draft PR while stacking agent-ready-for-review agent-blocked ready-for-human

Phases versus gates

A phase is a bounded agent turn. A gate is a parent-owned check. They are not the same thing: phases can edit and reason, gates measure the result and return pass, fail, or skipped.

Phase Runs through the selected engine, such as Codex SDK, Claude SDK, CLI fallback, or FakeEngine. It gets a prompt, a worktree, a timeout, and must finish with a promise line.
Gate Runs through Python-owned deterministic code. It executes commands or policy checks, captures logs, and decides whether Ralph may publish, repair, or block.
Agent phases
implement Agent writes the issue fix, runs narrow non-UI checks, commits, and emits COMPLETE or BLOCKED.
review Agent invokes swift-reviewer and spec-conformance-reviewer, fixes blocking findings, commits any remediation, then emits a promise.
ui-verify Agent runs UI verification and visual baseline review when the issue touches UI surfaces.
publish decision No agent owns this. Python decides whether to publish, repair, or preserve blocked work.
Parent gates
Non-UI gates swift-test, xcodegen-generate, Xcode unit/component tests, and swiftlint.
Authority gates UI-test edit authority is a mechanical check against the frozen issue contract.
UI-owned gates UI integration and Visual Regression failures can trigger the one repair cycle.
PR lifecycle gates Python checks labels, PRD stack readiness, closing keywords, draft state, and sanitized blocked reports.
Repair branch
repair-ui-gate Only runs after a first UI-owned gate failure when code exists. It receives a focused repair brief.
review-after-repair Runs only if the repair touched production Swift, tests, project files, or package configuration.
rerun once The relevant UI/full gate reruns exactly one time. Pass ships. Second failure becomes a blocked rescue PR.

Read it left to right: a phase may create or change code, then gates judge that state. A gate failure may cause a repair phase, but the gate itself is not an agent phase.

Key constraint: SDKs should not own Ralph. They only run the agent phase. Python remains the parent that decides gates, PR state, labels, repair, and blocked reports.
