Design Glossary

The house vocabulary from .claude/skills/codebase-design/SKILL.md, with each term pinned to a concrete example from this codebase. Use these words exactly — don't substitute "component," "service," "API," or "boundary."

TermDefinitionIn this codebase
Module Anything with an interface and an implementation — scale-agnostic: a function, class, or package. LoadSuggestionEngine (one function) and Progress (24 files) are both modules.
Interface Everything a caller must know to use the module correctly: signatures plus invariants, ordering constraints, error modes, and performance characteristics. SyncCoordinator's interface includes "flush happens before pull" — an ordering guarantee no type signature shows.
Implementation What's inside a module — the part below the waterline. The ~820 LOC of HTTP/JSON behind SheetsClient's five methods.
Depth Leverage at the interface: behaviour exercised per unit of interface learned. Not a line-count ratio — that framing is explicitly rejected. SessionCoordinator: supersets, rest, focus, transitions behind ~25 methods.
Seam A place where behaviour can be altered without editing in that place; where a module's interface lives. (Feathers) protocol SheetsClient — behaviour swaps from live Google to local fixtures without touching callers.
Adapter A concrete thing satisfying an interface at a seam — names the role, not the substance. GoogleSheetsClient, LocalWorkbookSheetsClient, and UITestFixture are three adapters at one seam.
Leverage What callers get from depth: more capability per unit of interface learned. One SheetLayoutInterpreter pays back at every read and every write (ADR-0003).
Locality What maintainers get from depth: change, bugs, and verification concentrate in one place. A cell-targeting bug is fixed once in the interpreter, fixed everywhere.

Rules of thumb

  • The deletion test — delete the module in your head: if complexity vanishes it was a pass-through; if it reappears across N callers it was earning its keep.
  • The interface is the test surface — callers and tests cross the same seam. Wanting to test past the interface means the module is the wrong shape.
  • One adapter is a hypothetical seam; two adapters is a real one — SheetsClient has three, so that seam has earned its existence.
  • Depth is a property of the interface, not the implementation — a deep module may have internal seams (private, for its own tests) behind its external one.
